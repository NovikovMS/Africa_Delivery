# ADR-001: Модуль бронирования реализован как модульный монолит

**Дата:** 2026-03-15

**Статус:** Accepted

## Контекст

TicketsHub готовится к сезону летних фестивалей. Модуль бронирования билетов —
наиболее критичный по нагрузке компонент системы: ожидается пиковая нагрузка
до 100 000 RPS при открытии продаж. Текущая система — монолит на Java
(Spring Boot) с единой PostgreSQL.

Ключевые архитектурные драйверы:
- Нагрузка: 100 000 RPS в пике, P95, задержка <200 мс.
- Консистентность: нулевые перепродажи (критично для бизнеса).
- Доступность: SLA 99.9%.
- Сроки: 3 месяца до начала сезона.
- Команда: 4 backend-разработчика на модуль, 2 DevOps.
- DevOps: CI/CD есть, но нет Kubernetes / оркестратора контейнеров.

Рассматривались три альтернативы:
1. Оставить в составе единого монолита.
2. Рефакторинг в модульный монолит с изолированными границами.
3. Выделение в отдельный микросервис.

### Альтернатива 1. Единый монолит
Плюсы: минимальные изменения, быстрый time-to-market.
Минусы: нет изоляции ресурсов, при пике бронирование конкурирует.
за пул потоков и подключения к БД с другими модулями (аналитика,
отчёты). Нет чётких границ — риск регрессий при изменении других модулей.

### Альтернатива 2. Модульный монолит
Плюсы: чёткие границы модулей, изолированные схемы данных, публичные
интерфейсы (Facades), готовность к будущему выделению в микросервис,
сохранение ACID-транзакций.
Минусы: требуется дисциплина тестирования (ArchUnit), накладные расходы на
публичные интерфейсы.

### Альтернатива 3. Микросервис
Плюсы: независимое масштабирование, собственная БД.
Минусы: потеря ACID-транзакций (нужен Saga), накладные расходы на сетевое
взаимодействие, нет Kubernetes для оркестрации, 3 месяца — слишком мало
для построения микросервисной инфраструктуры.

## Решение

Модуль бронирования реализован как модульный монолит в рамках единого
приложения TicketsHub. Применяются следующие принципы:
- Модуль имеет чёткие границы: BookingFacade как единственная точка входа
  для других модулей.
- Изолированная схема данных: таблицы bookings, seat_locks принадлежат
  только модулю бронирования.
- Взаимодействие с другими модулями через публичные интерфейсы
  (EventFacade, UserFacade).
- ArchUnit-тесты для тестирования границ модулей.
- Добавлены health-check- и readiness-точки для подготовки
  к будущему выделению в микросервис.

## Последствия

**Положительные:**
- Быстрая доставка: не нужно строить микросервисную инфраструктуру.
- Сохраняются ACID-транзакции: бронирование + блокировка места в одной
  транзакции.
- Чёткие модульные границы снижают риск регрессий.
- Подготовка к эволюции: при необходимости модуль можно выделить
  в микросервис с минимальными изменениями.

**Отрицательные:**
- Невозможно масштабировать модуль бронирования независимо.
- Единая PostgreSQL остаётся «бутылочным горлышком» при экстремальных пиках (>50 000 RPS).
- Команда должна соблюдать дисциплину модульных границ.

**Риски:**
- Если пиковая нагрузка превысит 50 000 RPS, потребуется выделение модуля
  в микросервис. Оценка разработки — 2–3 недели при наличии чётких интерфейсов.
- Конкуренция за пул подключений к PostgreSQL при одновременном пике
  бронирования и аналитических запросов.
